# Rails のレビュー観点

手順・重要度・結果の形は `dev-review` skill に従う。ここには Rails の変更で見る観点だけを書く。

## セキュリティ

- ストロングパラメータの抜け漏れがないか（マスアサインメント防止）
- SQL インジェクション（文字列で組み立てた `where`・`order`・`find_by_sql`）、XSS（`html_safe`・`raw`）のリスクがないか
- 認証・認可の抜け（他人のレコードを id だけで引けないか。`current_user` からたどっているか）
- 機密情報（トークン・パスワード・API キー）がハードコードされていないか。ログ・例外の通知に出ていないか（`filter_parameters`）
- `bin/brakeman` の警告がゼロか

## モデル

- バリデーションの抜け漏れ（presence / uniqueness / numericality）。DB の制約（`null: false`・一意インデックス・外部キー）とそろっているか
- uniqueness は、一意インデックスが無いと同時の書き込みで重複しうる
- enum の定義と DB の型・値が対応しているか
- コールバックに、他のモデルの更新や外部への送信など、読む人が予想しにくい副作用を持たせていないか

## マイグレーション

- 規約は `rails-migration-rules` skill に従う
- `null: false` と `default` の設定が適切か、ロールバックが安全に行えるか
- 必要なインデックスが含まれているか

## パフォーマンス

- N+1 クエリが発生していないか（`includes` / `preload` の必要性）
- 件数が増えると重くなる処理（全件の `each`、ループの中のクエリ、ページングの無い一覧）

## 非同期・トランザクション

- トランザクションの中でジョブの投入・外部への送信をしていないか（ロールバックしても送られる。`after_commit` などで外に出す）
- ジョブが 2 回動いても壊れないか（再試行で重複しないか）
- 同時に同じレコードを更新したときの競合（ロック・楽観ロック・一意制約）

## テスト

- 規約は `rails-test` skill に従う
- 正常系・異常系・境界値がカバーされているか。バリデーションの失敗ケースが明示的にテストされているか
- テストの期待値が仕様に合っているか（実装に合わせただけになっていないか）

## コード品質

- `bin/rubocop` の警告がゼロか
- 同名のローカル変数を Hash に入れる場合、省略記法（例: `foo:`）を使う
