# コードレビュー（共通）

品質・保守性・セキュリティの観点から厳しくレビューし、問題点は重要度（Critical / High / Low）を付けて具体的に指摘する。
差分に含まれる種類に応じて、観点の skill を読み足す。

- Rails（`app/`・`config/`・`db/`・`lib/`・`test/` の Ruby）→ `rails-review`
- React（`.jsx`・`.tsx`、React を使う `.js`・`.ts`）→ `react-review`

## 重要度

| 重要度 | 基準 | 扱い |
|---|---|---|
| Critical | 情報漏えい、認可回避、重大なデータ破壊など | 即座に作業を止めて人間へ報告 |
| High | 要件違反、主要機能の不具合、必要な検証の欠落 | 解消するまで完了にしない |
| Low | 軽微な改善 | 対象ブランチの責務に入るものは修正する。責務の外のものだけ、理由を残して GitHub Issue へ分離する（Issue 作成前は分離済みとしない） |

重要度に関わらず、対象ブランチの責務に入る指摘はそのブランチで修正する（今回の変更で生じたものか、前からあった見落としかを問わない）。

## セルフレビュー

すべての変更で行う。実装した会話の履歴を引き継がない別のセッション（レビュー役）が、読み取り専用で行う。実装者は名前の意味や分け方の理由を知っているため、自分のコードの読みにくさに気づきにくい。

レビュー役は、要件との一致、異常系、テストの妥当性、無関係な変更、仕様に書かれた対象からの逸脱、保守性（下記「保守性」）を確認する。

### 実行方法

- コミットしてから（作業ツリーに変更が無く、HEAD が対象と一致する状態で）依頼する
- Claude Code では、レビュー役の定義 `generic-self-reviewer` を名指しで起動する。汎用のサブエージェント、親の会話を引き継ぐ種類（fork）、起動時のモデルの上書きは使わない。レビューのたびに新しいセッションを起動し、前のレビュー役に続きを頼まない
- 依頼文に書くのは、作業ディレクトリ、回（初回・再レビュー①・再レビュー②）、仕様ファイルのパス（`dev-plan` skill の計画ファイルまたは仕様メモ）、base SHA・head SHA、この skill に従うこと、再レビューでは前回の結果と判定の記録のパス、に限る
- 依頼文に書かないもの: 実装の経緯や意図の説明、「問題ないはず」などの結論、実装者が選んだコードの抜粋。経緯を知らない目で読ませるためで、判断に必要な仕様（目的・受け入れ条件・対象と対象外）は仕様ファイルで渡す
- 読む深さと報告の量は差分に比例させる。誤字の修正に長い報告は求めない
- 実行失敗・結果欠落を「指摘なし」と扱わない。同じ依頼をやり直し、連続 3 回失敗したら止めて人間に確認する
- レビュー役を起動できない、結果の先頭でモデルが定義と違う・編集ツールを持っていると分かった場合は、別の種類・別のモデルで代わりにせず止めて人間に確認する

### 結果の形

レビュー役は次の 5 つを返す。

1. 自分のモデルの名前と ID（分からなければ「不明」）と、編集ツール（Edit・Write・NotebookEdit）を持っているか
2. 確認した内容（読んだファイルと、確かめた点）
3. 指摘。指摘ごとに ID・重要度（Critical / High / Low）・題・場所・根拠を書く。保守性の指摘もこの一覧に書く。無ければ「指摘なし」
4. 保守性の欄。下記「保守性」の表の項目ごとに、「確認した点」「該当なしと理由」「未検証と理由」のいずれかを書く。指摘にしたものは、その ID を添える
5. 未検証事項

### 記録

`.dev/reviews/<作業ID>/self_review_sessions/<回>-<head の先頭 7 桁>/` に残す（追跡対象外にする。作業 ID はブランチ名の `/` を `-` にしたもの、回は `initial`・`re1`・`re2`）。

- `request.md`: 先頭に使った種類とモデル、続けて依頼文
- `result.md`: レビュー役の結果の原文。実装者は要約・書き換えをしない
- `verdicts.md`: 指摘ごとの判定（妥当・一部妥当・不同意）、根拠、対応

PR 本文に、対象の head、指摘、判定と対応を書く。指摘が無い場合も、対象の head と「指摘なし」を書く。

### 指摘の扱い

- Critical: 作業を止めて人間へ報告する
- High: 解消するまで完了にしない。修正後に新しいセッションで再レビューし、解消をレビュー役が確認する
- Low: 上記「重要度」の扱いに従う。Low だけを直した場合は、再レビューせず、実装者が修正を確かめて `verdicts.md` に記録する
- 再レビュー②の時点で High が残る、または見解が分かれたままの指摘があれば、3 回目に入らず、双方の見解と根拠を示して人間に判断を求める。回を足すのは人間が指示した場合だけ
- 指摘が無ければ、それで十分とする。「指摘なし」を疑うための追加のレビューはしない

## 指摘の検証と反論

実装者は指摘を鵜呑みにせず、指摘ごとに妥当かどうかを検証してから対応する。

- 検証は、再現テスト（修正前に失敗すること）、コードの根拠、実際に動かした結果のいずれかで行う
- 判定は「妥当」「一部妥当」「不同意」のいずれかとし、根拠を記録する。重要度が過大・過小と判断した場合も根拠を残す
- 「今の環境では再現しないが起こりうる」ものは、その旨と根拠を記録し、対応するかを重要度に沿って判断する。判断がつかなければ人間に委ねる
- 不同意の指摘は修正せず、根拠を添えて再レビューに返す。レビュー役は根拠を検証し、指摘を維持・修正・取り下げのいずれかで答える。反論のやりとりは再レビューと同じ往復で数える
- 検証しても判断に必要な情報が足りない点は、推測で埋めずに不明点として示し、人間の判断に委ねる

## 保守性

すべての変更で確認する。

基準は「半年後に初めてこのコードを見る人（将来の自分を含む）が、変更する箇所と影響の範囲を、妥当な手間で特定できるか」。

| 項目 | 指摘にする根拠 |
|---|---|
| 責務 | 別々の理由で変わる処理が 1 つのメソッド・クラス・コンポーネントに結びつき、一方の変更で他方を壊しやすい |
| 名前 | 呼び出す側が、役割・単位・適用範囲を名前から誤解する |
| 重複 | 同じルール・同じ判定が複数の場所にあり、変更のたびに全部をそろえる必要がある |
| 値の直書き | 値の意味・単位・変えるべき場所が分からず、更新漏れを起こす |
| 一貫性 | 同じ役割なのに既存コードと違うやり方を使い、変更の手順や挙動を誤解させる。新しいやり方を持ち込む場合は、理由が PR 本文にあるか |

- 指摘には「どんな変更をするときに、何で困るか」を具体的に書く。その変更は、今の仕様・構造から現実的に想定できるものに限る。書けないものは好みの問題として、指摘にしない
- 責務の数、重複、直書きがあること自体は問題にしない。過剰な共通化や、追うのに手間がかかる間接参照も保守性を落とすため、同じ基準で指摘する
- 重要度: 次の変更で不具合や修正漏れを招く見込みが高いもの（例: 同じ判定が 2 か所にあり、片方だけ直される）は High、それ以外は Low
- 文書・ルールの変更は、次に読み替える: 正本と更新する場所が分かるか、同じルールの重複で更新漏れが起きないか、用語・リンク・手順が一貫していて次の担当者が実行できるか。コード向けの項目は「該当なし」と理由を書けば足りる

## 限界

別のセッションで行ったこと、レビュー役のモデルと編集ツールの有無、指摘を検証したことは、ルールと記録による抑止で、仕組みでは確かめていない。読み取り専用は、定義で編集ツールを外しているが、差分を読むためのシェルは残る。レビュー役は Claude 同士なので、同じ前提を見落とすことがある。
