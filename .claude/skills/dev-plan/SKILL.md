# 実装計画

着手前に以下を提示し、承認を得てから実装する。承認後は、その範囲で判断が確定している作業を確認なしで進める。
自明な小タスクは簡略可（フル計画は設計判断を含む中〜大タスク向け）。
簡略にする場合も、セルフレビューのレビュー役に渡す仕様メモとして、目的、受け入れ条件、対象 / 対象外の 3 点を下記「保存」のファイルに書く（各 1 行でよい。実装の経緯は書かない）。
フル計画は、人間に承認を求める前に、会話を引き継がないレビュー役のレビューを通す（下記「計画のレビュー」）。

## 計画に含める項目

- **目的 / 背景**: なぜこの変更が必要か
- **受け入れ条件**: 完了の定義（満たすべき条件）
- **対象 / 対象外**: 変更スコープと、あえてやらないこと
- **設計方針と代替案**: 採用案と、却下した案・その理由
- **DB・API への影響**: マイグレーション要否、API 契約の変更
- **セキュリティ / パフォーマンス**: 想定される懸念
- **テスト方針**: 正常/異常/境界、どの層のテストを書くか
- **段取り**: 実装ステップを詳細に列挙する
  - **順序**: 処理の上流から下流へ並べる（入口・トリガー → 中間処理 → データ層）。人間が読んで追える順にする
  - **粒度**: 各ステップは、対象のテストを併せて書いて green にできる最小単位まで細かく分ける。1 ステップ完了ごとに、追加したテストが通り、既存テストを壊さない状態を保つ
  - 上流が未実装の下流に依存する場合は、依存先をモック/スタブして green を保つ（または下流の最小実装を先に置く）
- **PR 分割**: 変更が大きい・複数の関心事に跨る場合、PR の分割案を提示する（各 PR の範囲と順序）
- **未決事項 / リスク**: 判断保留中の点、残存リスク
- **人間の承認が要るもの**: 下記「承認対象」に当たるもの

ユーザーが決めたことと、Claude が足した条件は分けて書く。

## 承認対象

次に当たる変更は、設計・変更範囲を人間に承認してもらってから実装する。

- 個人情報の収集・利用・保存・削除・外部送信、および実際の個人情報へのアクセス
- DB のテーブル・カラム・関連・制約・データ移行
- 認証・認可・トークン管理
- 依存関係とロックファイル
- 秘密情報、credentials、環境変数、外部接続先
- `CLAUDE.md`・skill・フック・CI など開発の仕組み自体
- 実データへの破壊的操作

加えて、次は区分とは別に扱う。

- UI の見た目の変更: 人間の目視確認を必須にする
- 仕様の変更（業務ルール・課金・権限など）: 仕様を人間に確認してから進める
- 設計の承認と実データ操作の承認は区別する

## 計画のレビュー

フル計画は、人間に承認を求める前に、計画を立てた会話の履歴を引き継がないレビュー役が、読み取り専用でレビューする。計画を立てた側は、会話で決まった前提を知っているため、計画に書き漏らした前提や検討の抜けに気づきにくい。簡略の計画は対象外。計画はレビュー役に作らせない。

### 実行方法

- 依頼する前にブランチ名を決め、計画の案を下記「保存」のファイルに書く（承認前の案であることを先頭に書く）
- 会話で人間が決めたこと・選んだ案は、計画ファイルに書く。レビュー役は計画ファイルだけを仕様として読む
- Claude Code では、レビュー役の定義 `generic-plan-reviewer` を名指しで起動する。汎用のサブエージェント、fork、モデルの上書きは使わない。レビューのたびに新しいセッションを起動する
- 依頼文に書くのは、作業ディレクトリ、回（初回・再レビュー）、計画ファイルのパス、この skill の「計画のレビュー」に従うこと、再レビューでは前回の結果と判定の記録のパス、に限る。計画の意図の説明や「問題ないはず」などの結論は書かない

### 観点

レビュー役は、計画ファイルと、計画が触れるコード・文書を自分で読み、次を確かめる。読む深さは計画の大きさに比例させる。

- 目的と受け入れ条件が対応し、受け入れ条件が確かめられる形で書かれているか
- 上記「計画に含める項目」に欠けが無いか
- 計画の前提が、今のコード・文書と合っているか（存在しないもの、既にあるものの作り直し、既存の決まりとの食い違い）
- 対象 / 対象外の線引きが目的に足りているか
- 設計方針の代替案に、検討すべき有力な案の抜けが無いか
- 承認対象の判定に漏れが無いか
- 段取りの順序と粒度、テスト方針（正常・異常・境界）が上記の決まりに沿っているか
- 計画の中で書いていない判断を、実装中に推測で埋めることにならないか

### 結果の形

1. 自分のモデルの名前と ID（分からなければ「不明」）と、編集ツール（Edit・Write・NotebookEdit）を持っているか
2. 確認した内容（読んだファイルと、確かめた点）
3. 指摘。指摘ごとに ID・重要度・題・場所・根拠を書く。無ければ「指摘なし」
   - High: このまま実装すると、目的・受け入れ条件を満たせない、承認対象の判定が漏れる、前提がコードと食い違う
   - Low: 書き方の改善、軽い検討の補足
4. 未検証事項

### 指摘の扱い

- 計画を立てた側が指摘を検証し、指摘ごとに判定（妥当・一部妥当・不同意）、根拠、対応を記録する。妥当な指摘は計画に反映する
- High を直した場合・High に不同意の場合は、新しいセッションで再レビューする（初回 → 修正 → 再レビュー の 1 往復まで）
- Low だけを直した場合は再レビューしない。Low に不同意の場合は、承認を求める際に両方の言い分を示す
- 再レビューで High が残る、または見解が分かれたままの指摘がある場合は、計画を直し続けず、両方の言い分を添えて人間に判断を求める
- 人間に承認を求めるときは、計画とあわせて、レビューの経過（各回の指摘、判定と対応、残った指摘）を示す

記録は `.dev/reviews/<作業ID>/plan_review_sessions/<回>/` に `request.md`（先頭に使った種類とモデル、続けて依頼文）・`result.md`（結果の原文）・`verdicts.md`（判定と対応）として残す。

## 止めて確認する条件

次に当たったら、その判断に依存する実装を止めて人間に確認する（形式はグローバルの CLAUDE.md の「判断を求めるとき」）。

- Critical を検出した
- レビューの往復の上限に達した: セルフレビューは再レビュー②、計画のレビューは再レビューの時点で High・見解が分かれたままの指摘が残る
- 同じ失敗に対する修正・再実行が 3 回失敗した
- 仕様・設計の判断が確定しない、承認範囲外の変更が必要になった、新たな承認対象が判明した
- 必要なレビューが実行失敗・結果欠落・モデル利用不可で完了できない（別モデルへ黙って切り替えない）

止めたときは、残る問題・試した対応・判断してほしい点を報告する。回答がないまま再開しない。

## 保存

計画は次のファイルに保存する（ブランチ単位、git 追跡対象外のローカル作業メモ）。

```
.dev/contexts/<ブランチ名の / を - にしたもの>.md
```

- `.dev/` を `.gitignore` に入れる（無ければ足すことを提案する）
- 耐久的な設計判断の理由は PR 本文に残す
- 承認前の案を先に書いた場合は、承認されたら承認済みの計画本体に置き換える
- 既存ファイルがあれば追記・更新する（別セッションの記録を尊重する）
