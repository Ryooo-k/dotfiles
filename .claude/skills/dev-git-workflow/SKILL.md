# git ワークフロー

## ブランチ

- main へ直接コミットしない。作業ブランチを作る
- ブランチ名は `<prefix>/<issue番号>-<説明>` の形式にする（例: `feature/15-create-cards-model`）
  - `feature/` — 新機能 ／ `refactor/` — リファクタリング ／ `fix/` — バグ修正 ／ `test/` — テストのみ

## コミット

- コミット前に、プロジェクトの必須チェック（lint・全テスト。Rails なら `bin/rubocop`・`bin/rails test`、フロントがあれば ESLint とそのテスト）を実行し、成功することを確認する
- メッセージは日本語で、**主題・空行・説明本文**の構成にする
  - 主題は変更内容を端的に表す 1 行にする
  - 本文には変更理由、設計上のポイント、守るべき挙動や互換性を簡潔に書く
  - ファイルごとの変更一覧や、diff を読めば分かる実装手順の列挙は避ける
- メッセージに issue 番号を含めない（PR 本文にだけ書く）。`Co-Authored-By` を含めない
- 承認済みの計画の範囲外でコミットする場合は、ブランチ・含めない変更・コミットの順序と完全なメッセージを示し、承認を得てから行う

例:

```text
補間MPに表示とカード操作可否を統一する

MPゲージと各操作の判定を同じ評価時刻に揃える。
時計購読を末端へ閉じ込め、画面全体の毎フレーム再描画を避ける。
```

## PR

- 関心事ごとに分ける。関心事が 2 つ以上になった時点（サーバーの修正、通信の部品、画面の見た目など）で、レビューに出す前に分け方を提案する。途中で範囲が足されたら、黙って同じブランチに足さず「別の PR にするか」を聞く
- 画面を伴う変更は、「見えない部品」と「画面」を別の PR にする前提で段取りを組む
- 本文は PR テンプレート（あれば）の欄に沿って書く。`gh pr create --body-file` ではテンプレートが自動で入らないため、欄を写して埋める
- 対応する issue 番号を本文に書く（例: `closes #15`）
- 本文には、レビューの経過（対象の head、指摘、判定と対応）と、人間に見てほしい点を書く。UI の変更は、起動の手順・見る画面・操作・見るべき状態を書く
- push と PR の作成は、プロジェクトのルールで確認なしが許されていない限り、ユーザーの確認を取ってから行う
- CI は PR の作成後に確認し、成功してから人間にマージを依頼する。マージは人間が行う
